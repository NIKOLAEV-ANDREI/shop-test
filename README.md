## Задание

## Цель

Разработать небольшой модуль для **PrestaShop 1.6**, который добавляет возможность хранить внутренние комментарии менеджеров к заказу.

Задание максимально приближено к типовым задачам по поддержке существующего интернет-магазина: необходимо разобраться в структуре проекта, механизмах расширения PrestaShop и работе с базой данных.

Глубокое предварительное знание PrestaShop не требуется. Можно пользоваться документацией, поиском, IDE и другими привычными инструментами разработки.

## Задача

Необходимо реализовать модуль:

```text
managercomment
```

Модуль должен добавлять к заказу внутренние комментарии сотрудников магазина.

### Функциональные требования

На странице просмотра заказа в административной панели PrestaShop должен появиться блок примерно следующего вида:

```text
Комментарии менеджеров

Алексей Федоров
17.08.2026 14:35
Связаться с клиентом перед отправкой.

[ Редактировать ]

Иван Петров
17.08.2026 15:10
Клиент подтвердил адрес доставки.

--------------------------------------------

Новый комментарий

┌─────────────────────────────────────────────┐
│                                             │
│ Текст комментария                           │
│                                             │
└─────────────────────────────────────────────┘

[ Добавить комментарий ]
```

Точный внешний вид интерфейса остается на усмотрение кандидата.

Комментарии предназначены только для сотрудников магазина и не должны отображаться покупателю.

Необходимо реализовать:

1. Возможность добавлять **несколько комментариев к одному заказу**.
2. Сохранение автора каждого комментария.
3. Отображение имени сотрудника, добавившего комментарий.
4. Сохранение даты создания комментария.
5. Возможность редактирования комментария.
6. Пользователь может редактировать **только собственные комментарии**.
7. Пользователь не должен иметь возможности редактировать комментарии других сотрудников.
8. После повторного открытия заказа все ранее добавленные комментарии должны корректно отображаться.
9. Комментарии разных заказов не должны смешиваться.

## Валидация комментария

Валидация должна обязательно выполняться **на стороне backend**.

Требования к длине комментария:

* минимальная длина — **5 символов**;
* максимальная длина — **500 символов**.

Если комментарий не соответствует этим требованиям, он не должен сохраняться.

Пользователь должен получить понятное сообщение об ошибке.

Frontend-валидацию также можно добавить, но она не должна заменять backend-валидацию.

Следует учитывать как минимум следующие случаи:

```text
"abc"
```

Такой комментарий не должен сохраниться, так как он короче 5 символов.

Комментарий длиной более 500 символов также не должен сохраниться.

Продумайте поведение для строки, состоящей только из пробелов.

## Работа с пользователями

Для каждого комментария необходимо определить текущего авторизованного сотрудника PrestaShop и сохранить информацию об авторе.

В интерфейсе рядом с комментарием должно отображаться имя сотрудника.

Например:

```text

```

Способ хранения информации об авторе остается на усмотрение кандидата.

При этом следует учитывать, что имя сотрудника в системе в будущем может измениться.

Если это влияет на выбранную структуру хранения данных, кратко объясните принятое решение.

## Права на редактирование

При редактировании комментария необходимо проверять права **на backend**, а не только скрывать кнопку в интерфейсе.

Например, если пользователь вручную отправит запрос на изменение чужого комментария, сервер должен отклонить этот запрос.

Условие:

```text
Автор комментария == текущий пользователь
```

только тогда комментарий может быть изменен.

Продумайте, какое сообщение или HTTP-поведение должно возникать при попытке изменить чужой комментарий.

## Реализованное решение

Модуль `managercomment` добавляет внутренние комментарии сотрудников к заказам в административной панели PrestaShop 1.6.

Комментарии отображаются только сотрудникам, имеющим доступ к странице заказа в административной панели. Покупателям на витрине и в истории заказов они не показываются.

### Возможности

* добавление нескольких комментариев к одному заказу;
* сохранение ID и имени сотрудника;
* сохранение даты создания и последнего изменения;
* отображение комментариев после повторного открытия заказа;
* редактирование только собственных комментариев;
* backend-валидация длины от 5 до 500 символов;
* отклонение строк, состоящих только из пробелов;
* отображение признака и даты редактирования;
* изоляция комментариев разных заказов.

### Установка модуля

1. Скопировать папку `managercomment` в каталог `modules` установленного магазина PrestaShop 1.6.
2. В административной панели открыть раздел **Modules and Services**.
3. Найти модуль **Комментарии менеджеров**.
4. Нажать **Install**.
5. Открыть любой заказ в разделе **Orders**.

При установке модуль:

* создаёт таблицу `{DB_PREFIX}manager_comment`;
* регистрируется в хуке `displayAdminOrder`.

В локальном Docker-окружении папка модуля подключается автоматически:

```yaml
./managercomment:/var/www/html/modules/managercomment

```

При удалении модуля таблица комментариев и все находящиеся в ней данные удаляются. Это решение выбрано для полного удаления данных модуля и отсутствия неиспользуемых таблиц после деинсталляции.

### Архитектурные решения

Модуль использует хук `displayAdminOrder`. Изменения core файлов и overrides не используются.

Комментарии хранятся в отдельной таблице `{DB_PREFIX}manager_comment`. Для каждой записи сохраняются:

* ID заказа;
* ID сотрудника;
* имя сотрудника на момент создания;
* текст комментария;
* дата создания;
* дата последнего изменения.

Одновременно сохраняются `id_employee` и `employee_name`. ID используется для проверки авторства, а имя хранится как снимок. Поэтому изменение или удаление сотрудника в будущем не меняет имя автора уже созданного комментария.

Внешние ключи на таблицы PrestaShop не используются, чтобы не связывать жизненный цикл таблицы модуля с core-таблицами. Перед добавлением комментария существование заказа проверяется в PHP.

Для таблицы созданы индексы:

* `idx_order_date (id_order, date_add)` — получение комментариев заказа и аналитические запросы;
* `idx_date_add (date_add)` — получение последних комментариев;
* `idx_employee (id_employee)` — выборка комментариев сотрудника.

Комментарии выводятся в хронологическом порядке. При одинаковой дате дополнительная сортировка выполняется по ID комментария.

После успешного добавления или редактирования применяется перенаправление на страницу заказа. Это предотвращает повторную отправку формы при обновлении страницы.

### Проверка авторства

Текущий сотрудник определяется на backend через `$this->context->employee`. ID автора не принимается из формы.

Форма редактирования отображается только тогда, когда `id_employee` комментария совпадает с ID текущего сотрудника. Эта проверка отвечает только за интерфейс и не считается достаточной защитой.

При обработке POST-запроса модуль повторно:

1. получает комментарий по ID комментария и ID заказа;
2. сравнивает его `id_employee` с текущим сотрудником;
3. отклоняет запрос при несовпадении;
4. выполняет `UPDATE` с дополнительными условиями по ID комментария, заказа и сотрудника.

При попытке изменить чужой комментарий выводится сообщение:

```text
Вы можете редактировать только собственные комментарии.
```
Чужой комментарий и дата его изменения остаются без изменений.

### Backend-валидация

Перед добавлением и редактированием комментария сервер:

1. проверяет, что получено строковое значение;
2. удаляет пробелы по краям через `trim()`;
3. вычисляет длину через `Tools::strlen()`;
4. требует длину от 5 до 500 символов включительно.

Строки, состоящие только из пробелов, после `trim()` становятся пустыми и отклоняются.

HTML-атрибуты `minlength`, `maxlength` и `required` используются только для удобства. Полная проверка повторяется на backend, поэтому обход браузерных ограничений не позволяет сохранить некорректный текст.

Для SQL-значений используются приведение ID к `int` и функция `pSQL()`. При выводе имени и текста применяется Smarty-фильтр `escape:'html':'UTF-8'`.

### Как проверить работу

1. Войти в административную панель PrestaShop под сотрудником.
2. Открыть раздел **Orders** и выбрать заказ.
3. Добавить комментарий длиной от 5 до 500 символов.
4. Убедиться, что рядом с комментарием отображаются имя сотрудника и дата создания.
5. Добавить ещё один комментарий и повторно открыть заказ.
6. Открыть другой заказ и убедиться, что комментарии первого заказа там отсутствуют.
7. Отредактировать собственный комментарий и проверить изменение текста и `date_upd`.
8. Войти под другим сотрудником и убедиться, что форма редактирования чужих комментариев не отображается.
9. Подменить `id_manager_comment` в HTML-форме и отправить запрос на изменение чужого комментария. Сервер должен отклонить запрос с сообщением:

```text
Вы можете редактировать только собственные комментарии.
```

Для проверки backend-валидации можно временно изменить HTML-ограничения формы через инструменты разработчика браузера:

* строка из пробелов должна быть отклонена;
* текст короче 5 символов должен быть отклонён;
* текст длиннее 500 символов должен быть отклонён.

Покупателю комментарии не отображаются, потому что модуль зарегистрирован только в административном хуке `displayAdminOrder`.

### SQL-запросы

Аналитические SQL-запросы находятся в файле:

```text
sql/order_comments.sql
```

В файле находятся запросы:

1. последние 100 комментариев с информацией о заказе, клиенте и сотруднике;
2. топ-5 заказов по количеству комментариев;
3. последние 3 заказа без комментариев.

Запросы используют префикс `ps_`. Если магазин установлен с другим префиксом, его необходимо заменить в SQL-файле.

Запуск SQL-файла в PowerShell:

```powershell
$sqlText = Get-Content -Raw .\sql\order_comments.sql
$sqlText | docker compose exec -T db mysql --default-character-set=utf8 -uprestashop -pprestashop prestashop
```

### Известные ограничения

* добавление и редактирование выполняются обычными POST-формами без AJAX;
* при большом количестве комментариев пагинация отсутствует;
* удаление комментариев не реализовано;
* автоматические тесты отсутствуют, проверка выполняется вручную;
* при попытке изменить чужой комментарий отображается сообщение об ошибке, отдельный HTTP-ответ `403 Forbidden` не используется;
* SQL-файл использует стандартный префикс `ps_`;
* Docker Compose не использует постоянные тома для базы и файлов PrestaShop, поэтому для сохранения установленного магазина следует использовать `docker compose stop` и `docker compose start`, а не удалять контейнеры.
